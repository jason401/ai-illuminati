# 하위방 병렬 작업 — 구조 계획 (확정, 2026-11-17)

구현은 TODO 보드의 P0~P4 순서로 한다. 각 단계는 앞 단계가 main에 들어간 뒤 시작.

목표: 메인방(1)의 AI가 일을 나눠 하위방(2), (3)에 맡기고, 자기 몫을 한 뒤 결과를 합쳐 검증·push한다.
같은 repo를 여러 AI가 **동시에 고치는 것**을 처음부터 지원한다. 코드는 아직 건드리지 않았다.

## 2. 잠금 구조 바꾸기 (핵심)

### 지금
`ProjectWork.acquire` (`app/modules/AIProjects/ProjectWork.swift:397`)는 Git **common dir 하나당 쓰는 사람 하나**.
worktree를 따로 만들어도 common dir이 같아서 막힌다. `isHeld`, TODO 스케줄러, `busy`도 전부 common dir 기준.

### 바꾼 뒤: 두 층 잠금

1. **작업 폴더(worktree) 잠금 — 배타적.**
   키 = `git rev-parse --show-toplevel`을 정규화한 경로. 한 worktree에는 한 명만 쓴다.
   지금 `held[commonDir]`가 하던 일을 `held[worktree]`가 한다.
2. **repo 작업 잠금 — 짧게, 따로.**
   키 = `"refs:" + common dir` (작업 폴더 잠금 파일과 **이름이 겹치지 않게** 접두어를 붙임. 지금은 조상 폴더에 공유 잠금을
   거는데, 같은 이름을 쓰면 worktree 배타 잠금과 부딪힘).
   - 턴 동안에는 **아무도 이 잠금을 들고 있지 않는다.** 공유 잠금을 쥔 채 배타로 "올리는" 일이 없으니 교착도 없다.
   - ref를 바꾸는 앱 Git 동작만, 그 명령이 도는 동안 배타로 잡는다 (최대 60초 기다림, 순서대로):
     worktree 만들기/지우기, 브랜치 만들기/전환, 합치기, fetch/pull, push(턴 끝 지연 push 포함), stable 공개.
     **목록을 따로 적지 않고 `GitLink`의 모든 ref 변경 진입점에 일괄 적용** (빠뜨림 방지).
   - 커밋은 이 잠금 없이 한다: 서로 다른 브랜치·각자의 index라 Git이 ref 단위로 알아서 잠근다.
     앱의 `ProjectProcess.git`은 hook을 끄고 돌므로 hook끼리 부딪칠 일도 없다.

앱 인스턴스 간에도 같은 규칙: 지금 쓰는 `lockFile`(flock) 방식 그대로. worktree는 `LOCK_EX`(즉시 실패), refs는 `LOCK_EX`(잠깐 기다림).
정렬된 순서로 한 번에 잡는 규칙(교착 방지)도 그대로.

### 바뀌지 않는 것
- 문서 프로젝트(Git 없음) 규칙, 일반 연결 폴더 규칙 그대로.
- 메인 worktree에는 여전히 한 명만 → 일반 채팅·TODO가 메인 폴더를 동시에 고치는 일은 지금처럼 막힘.
- 앱 밖 편집기/에이전트는 여전히 못 막음 (지금과 같음).

### 같이 고칠 곳
- `isHeld(root)`: common dir이 아니라 그 root의 worktree 기준. TODO는 "그 worktree가 바쁠 때만" 기다림.
- `busyKorean` 문구: "다른 AI가 지금 **이 폴더**를 고치는 중" 정도로.
- `docs/CODING_MODE_PLAN.md:99` "worktree도 같은 repo로 직렬화" 문장 갱신, `docs/MODULES.md:477` 약속 줄 갱신.
- 지켜야 할 git 규칙: 같은 브랜치를 두 worktree에 체크아웃 불가(Git이 막음). 메인방의 `git_switch`가 `sub/` 브랜치로 가는 것도 앱이 막음.

## 3. 하위 작업 폴더(worktree)

- **위치: repo 밖**, 앱 데이터 폴더 `…/AI Illuminati/worktrees/<repo 해시>/<분할 id>-<n>/`.
  repo 안에 두면 메인방 AI의 쓰기 범위에 하위방 파일이 포함돼 서로 침범함.
- **브랜치:** `sub/<분할 id>/<n>` (로컬 전용). push 허용 목록(main/feature/fix/codex)에 없으니 하위방은 자동으로 push 불가.
- **출발점:** 나누는 순간의 메인방 HEAD. **메인방 작업 트리가 깨끗해야 나눌 수 있음.**
  공유 계약(인터페이스, 빈 함수, 계약 테스트)이 필요하면 메인방이 먼저 "계약 커밋"을 하고 나눔
  — 이전 시험 세 번이 성공한 방식 (`docs/modules-history.md:85`).
- **하위방 권한:** 자기 worktree만 쓰기, 원래 repo와 다른 공유 폴더는 읽기 전용. `workBinding`을 worktree 경로로 만들면 됨.
- **정리:** 합치기와 push가 성공하면 worktree와 브랜치 삭제. 실패·취소 시에는 **남겨두고** 사용자에게 "버리기/이어하기" 카드.

### 등록 명령(테스트/빌드)
- worktree에도 `.ai-illuminati.json`이 있으니 `project_run`은 그 worktree에서 실행.
- 무거운 테스트가 동시에 셋 돌면 느리고, 테스트 캐시 잠금(`test-cache.lock`)과 부딪칠 수 있음 → **repo당 `project_run`은 한 번에 하나, 나머지는 줄 서기.** 하위방은 `--affected` 빠른 테스트, 전체 테스트는 합친 뒤 메인방에서 한 번.

## 4. 흐름

```
메인방(1)                       하위방(2)            하위방(3)
 ├ 일을 보고 나눌지 판단
 ├ delegate_plan(나눌 계획) ──▶ [사용자 승인 카드 / FULL AUTO면 자동 승인]
 ├ (필요하면) 계약 커밋
 ├ 앱이 worktree 2개 + 하위방 2개 생성 ─▶ 작업 1 시작   작업 2 시작
 ├ 자기 작업 3 진행               │                    │
 ├ delegate_message("함수 이름 X로") ─▶ 다음 턴에 반영    │
 ├ 자기 작업 3 커밋               커밋 + 보고         커밋 + 보고
 ├ delegate_result(기다림 ≤300초, 반복 호출)
 ├ 합치기: 충돌 미리 검사 → merge → 범위 밖 파일 확인
 ├ 전체 테스트 → 다른 AI 리뷰 → push
 └ worktree/브랜치 정리
```

### 메인방 AI가 쓰는 도구 (회의 도구와 같은 모양)
| 도구 | 하는 일 |
|---|---|
| `delegate_plan` | 작업별 목표·맡을 파일·건드리면 안 되는 파일·맞물리는 지점·끝 조건을 내고 승인 카드를 띄움. 맡을 파일이 겹치면 앱이 거절 |
| `delegate_status` | 각 하위방 상태(진행/보고됨/막힘/실패) |
| `delegate_result` | 기다렸다가 보고(요약, 커밋, 바뀐 파일, 테스트 결과)를 받음 |
| `delegate_message` | 진행 중인 하위방에 메시지를 줄 세움 (`PendingInputs` 재사용) |
| `delegate_cancel` | 하위방 하나 멈춤 |
| `git_merge_sub` | 앱이 하는 합치기 (아래 5번) |
| `delegate_resync` | 충돌 난 하위방에 최신 메인을 넣어 주고 다시 맡김 (아래 5번 6a) |

### 하위방 AI가 쓰는 도구
| 도구 | 하는 일 |
|---|---|
| `sub_report` | 끝: 커밋한 뒤 요약 보고. 이걸 불러야 "보고됨" |
| `sub_blocked` | 막힘: 질문을 남기고 멈춤 → 메인방 `delegate_result`에 질문으로 옴 |

하위방에는 `delegate_*`, `git_push`, `git_pull`, `git_switch`, `git_publish_stable`이 없다.

### 메인방 턴이 먼저 끝나버리면
CLI 한 턴에는 시간 한계가 있다. 메인방 턴이 하위방보다 먼저 끝나면, **하위방이 모두 끝났을 때 앱이 메인방에 "합류 턴"을 자동으로 하나 넣는다**
("하위 작업 결과가 도착했어요. 합쳐 주세요"). TODO 스케줄러가 다음 일을 시작하는 방식과 같다.
- "끝"은 보고됨·막힘·실패·취소 모두 포함 → 하나가 실패해도 메인방이 멈춰 있지 않음.
- 합류 턴은 분할 id당 한 번만 (기록에 "합류 턴 넣음" 표시; 재시작·중복 보고에도 두 번 안 생김).
- 동시 실행 수: 메인방이 턴 안에서 기다리는 동안은 한 자리를 차지함. 턴이 끝나 기다리기만 하는 메인방은 자리를 차지하지 않음.
  하위방은 분할을 승인할 때 자리를 미리 확보하고, 자리가 없으면 줄 섬 (TODO에 자리를 뺏기지 않게).
- TODO 스케줄러의 `isHeld`: 그 TODO가 쓸 worktree가 바쁠 때, 그리고 refs 잠금을 기다리는 작업이 있을 때 기다림.
  하위 worktree는 그 분할 전용이라 TODO가 잡지 않음.

## 5. 합치기 (`git_merge_sub`, 앱이 실행)

1. **합칠 하위방은 "보고됨" 상태여야 한다**: 그 턴이 끝났고 worktree 잠금도 풀렸어야 함 (합치는 중에 하위방이 더 쓰지 못함).
   합치는 대상은 브랜치 이름이 아니라 **`sub_report` 때 기록한 커밋 SHA**. 그 SHA가 출발 커밋의 후손인지 확인.
2. refs 잠금을 잡는다. 메인 worktree가 깨끗한지 확인 (메인방은 작업 3을 먼저 커밋).
3. 하위방 하나씩: **지금의 메인 HEAD 기준으로** `git merge-tree --write-tree` 충돌 미리 검사
   (`docs/APP_PARALLEL_TRIAL.md:21`에서 이미 시험함). 두 번째 하위방은 첫 번째를 합친 뒤의 HEAD로 다시 검사.
4. 맡은 파일 밖을 바꿨으면 경고를 메인방 AI에게 돌려줌 (막지는 않음; AI가 판단해 받거나 돌려보냄).
5. 충돌 없으면 `git merge --no-ff <SHA>` → 누가 무엇을 했는지 커밋 기록에 남음.
   미리 검사는 통과했는데 merge가 실패하면 (드묾) `git merge --abort`로 merge 전 상태로만 돌리고 보고.
   이것은 앱이 방금 시작한 merge만 되돌리는 것이라 "자동 reset 없음" 규칙과 부딪치지 않음.
6. 충돌 나면 merge는 하지 않고 충돌 파일 목록을 돌려줌. 메인방 AI는 고름:
   (a) **`delegate_resync`**: 앱이 하위 worktree에서 최신 메인을 하위 브랜치에 merge해 두고(충돌 표시 그대로) 하위방에 다음 턴을 줌
       → 하위방이 충돌을 풀고 다시 `sub_report`. (하위방은 pull/switch가 없으니 이 길이 필요)
   (b) 메인방이 직접 merge해 충돌을 품 — 메인 worktree에서 진행, 평소 작업과 같음.
   (c) 사용자에게 물음.
   자동 stash/강제 덮어쓰기 없음 (지금 규칙 유지).
7. 첫 번째는 합쳤고 두 번째에서 멈춘 상태도 정상 상태로 취급: 분할 기록에 하위방별 "합쳐짐/대기/충돌"을 남김.
8. 다 합친 뒤 전체 테스트 → 기존 리뷰 단계 → `git_push`(턴 끝에 한 번, 지금과 같음).

## 6. 멈춤·재시작·되돌리기

- **메인방 Stop** → 하위방 전부 멈춤. worktree는 남기고 "버리기/이어하기" 카드.
- **하위방 하나 실패/사용량 한도** → 지금처럼 다른 계정이 같은 worktree에서 이어받음. 안 되면 "실패"로 보고 → 메인방이 직접 하거나 사용자에게 물음.
- **앱 재시작** → 분할 기록(앱 데이터 폴더의 `splits/<메인방 id>.json`: 하위방 id, worktree, 브랜치, 출발 커밋, 보고 SHA, 하위방별 상태)으로 복구.
  **자동 재개는 안 함** (`CODING_MODE_PLAN.md`의 규칙과 같음). 메인방에 "이어하기/버리기" 카드.
  - 기록을 **먼저** 쓰고("만드는 중") worktree를 만든 뒤 "준비됨"으로 바꿈 → 중간에 꺼져도 남은 worktree를 찾을 수 있음.
  - 재시작 때 `git worktree list`와 기록을 맞춰 봄: 기록에만 있음(폴더 사라짐), 폴더만 있음, 반쯤 된 merge(`MERGE_HEAD` 있음)를 각각 카드로 보여줌.
  - push는 됐는데 정리 전에 꺼진 경우: push된 HEAD에 하위 SHA가 들어 있으면 정리만 다시 함.
  - 분할 기록에는 repo 경로와 common dir을 같이 남겨 repo가 옮겨졌으면 "찾을 수 없음"으로 멈춤.
- **계정 넘기기와 정리** → 기존 `ProjectRun.nextAttempt/endAttempt` 규칙 그대로: 이전 프로세스와 도구 세션이 끝났다고 확인된 뒤에만
  다음 AI가 쓰거나 worktree를 지움.
- **오래 남은 worktree** → 하루 지난 정리 안 된 분할은 메인방과 프로젝트 정보 화면에 알림.
- **Undo/백업** → worktree마다 따로. 하위방 Undo는 자기 worktree만. 이미 합친 변경은 커밋이라 되돌리기는 `git revert`로 (자동 아님).

## 7. 승인 카드가 너무 많아지는 문제

- FULL AUTO: 지금처럼 등록 명령은 승인 없이 실행.
- 그 외: 하위방의 승인 요청은 **메인방 카드에 모아서** 보여줌 ("하위방 2: test 실행").
  같은 분할 안에서 **완전히 같은 명령**이면 "이번 분할 동안 허용" 버튼 하나로. 다른 명령은 매번 승인. (권한을 넓히는 게 아니라 같은 승인을 한 번에 누르는 것)
  "같다"의 기준은 명령 이름이 아니라 **실행 파일 실제 경로 + 인자 + 그 worktree + `.ai-illuminati.json` 내용 해시 + 권한**.
  하위방이 스크립트나 설정을 고쳤으면 다시 승인 받음.

## 8. 언제 나누나 (AI에게 주는 기준)

나눈다:
- 서로 기다리지 않고 진행할 수 있다 (ChatGPT(개인) 기준).
- 맡을 파일이 겹치지 않는다.
- 맞물리는 지점이 있으면 계약 커밋으로 먼저 고정할 수 있다.
- 각 몫이 혼자 해도 몇 분 넘게 걸릴 크기다.

안 나눈다: 한 파일 안의 작업, 서로 얽힌 로직, 몇 줄짜리 수정, 원인을 아직 모르는 버그.

## 10. 단계

| 단계 | 내용 | 끝 조건 |
|---|---|---|
| P0 잠금 | 두 층 잠금만. 기능 변화 없음 | 기존 테스트 통과 + 새 테스트: 같은 repo 다른 worktree 둘 동시 쓰기 OK / 같은 worktree 둘 거절 / refs 잠금 중 다른 push·pull은 기다림, 커밋은 그대로 됨 / 앱 인스턴스 간 lock 파일 / 문서 프로젝트 규칙 그대로 |
| P1 worktree·합치기 | worktree 생성·정리, `git_merge_sub`, 하위 브랜치 push 금지 | 임시 repo에서 충돌 없음/충돌 있음/범위 밖 파일 세 경우 테스트 |
| P2 분할 | `delegate_*`, `sub_*`, 하위방 생성, 합류 턴, 분할 기록, Stop 연쇄 | 가짜 AI(테스트용 응답기)로 2개 분할→보고→합치기 흐름 테스트, 재시작 복구 테스트 |
| P3 화면 | 진행 카드, 사이드바, 모은 승인 카드 | 미리보기 렌더(`render_chat.sh`) |
| P4 실제 시험 | `APP_PARALLEL_TRIAL.md`의 Accounts/Localization 계약을 실제 하위방으로 다시 돌림 | 전체 테스트 통과, 걸린 시간을 혼자 했을 때와 비교 |

P0은 그것만으로도 쓸모가 있다: 사용자가 직접 worktree를 열어 두 채팅에 연결하면 바로 병렬 작업이 된다.

- 하위방 AI 종류: 기본은 회의처럼 남은 사용량으로 고름. 사용자가 "Codex에게 맡겨" 같이 지정할 수 있게 할지.
